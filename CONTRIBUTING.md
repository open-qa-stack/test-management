# Contributing to Open QA Stack

Thank you for looking at the code. The bar is high on purpose: strict TypeScript, tests that cover every line and every branch, and commits that can each be delivered.

## The agreement

Contributions are accepted under the [contributor license agreement](CLA.md): you keep your copyright, the project keeps one legal basis. On your first pull request you are asked to sign it, once, by a comment; a check reminds you and holds the merge until the signature is recorded. It is not an assignment: it grants the maintainer a license broad enough to defend the code, answer for its provenance and adapt how the project is licensed without tracking down every past author. If you contribute for an employer, the employer signs it as an entity.

## Checking a change

`pnpm check`, run at the root of the repository with the Node.js `.nvmrc` names, tells whether a commit can be delivered. It runs the steps below in order, stops at the first that fails, names it, and changes no file.

1. **typecheck**: `tsc` in strict mode on every package and on the lint rules of the workspace.
2. **lint**: oxlint with type information and the lint rules of the workspace, in `lint/`, warnings denied, then the check of the manifests against [the package boundaries](#package-boundaries). An explicit `any` fails.
3. **format**: Prettier, without rewriting anything. `pnpm format` rewrites the files it would change.
4. **build**: the `build` script of every package that has one. The packages that run their TypeScript sources as they are have none.
5. **coverage directives**: a comment that leaves code out of the coverage, `v8 ignore`, `istanbul ignore`, `c8 ignore`, `node:coverage ignore` or `node:coverage disable`, gives in a source file, on its line or the line before, the URL of the issue of this repository that explains it, such as `https://github.com/open-qa-stack/test-management/issues/1`.
6. **secrets**: no file of the index holds a secret, by the rules of [the scan](#scanning-before-publishing).
7. **tests and coverage**: every test of the workspace, which together cover 100 % of the lines, branches and functions of every file of code under the `src` folder of each package, files no test loads included. `pnpm test` runs them with [Vitest](https://vitest.dev), one project per package, their test files side by side in a pool of processes sized to the machine; `pnpm test:watch` runs again those a change touches. A test of the console in Chromium that fails leaves in `.vitest/failures/` a capture of its page and what the page logged, under the name of the test; the continuous integration keeps that folder as the `failures-*` artifact of a part that failed. `pnpm exec vitest run --project agents designer` runs the files of one package whose name holds a word. The package `check`, whose tests start programs of their own, keeps a `test` script, and runs beside the others: what a program started by a test covers is measured by Node.js, which the coverage of Vitest does not read. Its script runs its tests with Vitest, its modules loaded as Node.js loads them, and reports what Node.js measured, in the tests and in the programs they start, with [c8](https://github.com/bcoe/c8). The project `api` is compiled by [SWC](https://swc.rs) rather than by esbuild, as NestJS reads the types of constructors, which esbuild does not keep; the two programs of the package, `main.ts` and `migrate.ts`, which its tests start from its build, are listed under `coverage.runAsProgram`. Tests, scripts, fixtures and configuration files live outside `src` and are not measured, and neither is a file that only declares types. The check reads what was covered from the reports of the test runners: a script that lowers a threshold or leaves a file out of the measure changes nothing, and a file of code missing from a report fails. Every program it starts keeps its temporary files in one folder of the run, which the check removes once it ends, so that the folders a test leaves behind do not pile up. It removes the reports once read; with `OQAS_COVERAGE_REPORT` naming a file, relative to the root, it keeps them there as one report in the LCOV format, every path from the root, for a tool that reads the coverage. A module that only runs in a browser, listed under `coverage.measuredInBrowser` in the manifest of its package, is left to the tests of that package, which measure it there; an entry point the tests start as a program of its own is listed under `coverage.runAsProgram`. The tests of `store` and of `api` that go through a database are written once and run on the two it supports: a SQLite file, and a real PostgreSQL server, which each of the two runs starts in a container and removes. They need Podman or Docker, as [the database](packages/store/docs/database.md#tests) tells; `pnpm exec vitest run --project store` runs those of the store on SQLite alone, with nothing beside them.

The tests of some packages alone are enough for a change that touches them alone. `pnpm check --affected origin/main` tests the packages the change touches since the revision it shares with `origin/main`, files not yet committed included, and every package that depends on one of them, then requires their coverage alone; a change outside the packages, but for the documents of the workspace (the Markdown files of the root and `docs/`), touches every package. `pnpm check --packages apps/web,@open-qa-stack/cli` does the same for the packages named, by folder or name. The code of a package is covered by its tests and by those of the packages that use it, so neither tests a package without its dependents. The other steps run on the whole workspace either way.

The continuous integration runs the check on several machines at once. `pnpm check --only static` runs the steps before the tests, and `--only tests` the tests alone. `pnpm check --part 2/4` runs the second of four parts of the test files of the root, with the `--shard` of Vitest, and writes what they found and covered to `.vitest/blob/`, holding no threshold; its journal names each test that failed. The parts are balanced by how long each test file took, which `test-durations.json` keeps at the root: to refresh it, put the `tests-*` reports of a run of `main` in `.vitest/blob/`, then run `pnpm test:durations`. A file it does not know counts as long as the median one. `--part own` runs the packages with a test script of their own, and `--part own:packages/check` one of them alone, named by its name or its folder. `pnpm check --merge` then reads the reports of every part as one run, and requires the coverage of the packages the root tests. Each takes `--affected` or `--packages` too: a pull request tests the packages it touches since its base branch, `main` every package.

Once the dependencies are installed with `pnpm install --frozen-lockfile`, the check needs no network. One dependency is a native module, better-sqlite3, which runs SQLite: its package holds the binary of the usual platforms, so the install needs no compiler — [the database](packages/store/docs/database.md#sqlite) says what to do on another.

## Package boundaries

Each package depends only on the packages its row names. `pnpm lint` refuses any other import in the sources of a package, under its `src` folder, whatever its form: the name of the package or a path into it, a relative path out of the folder of the package or through its `node_modules`, a dynamic import or a `require` of a constant string, an `import … = require(…)`, a type-only import or a re-export. It refuses the same dependency in the `dependencies`, `peerDependencies` and `optionalDependencies` of the manifest of the package. Each refusal names the file, the line, the package, what it imports and the rule.

| Package   | Folder             | Depends on                                                     |
| --------- | ------------------ | -------------------------------------------------------------- |
| `domain`  | `packages/domain`  | nothing                                                        |
| `store`   | `packages/store`   | `domain`                                                       |
| `api`     | `apps/api`     | `engine`, `store`, `domain`                                    |
| `harness` | `packages/harness` | `domain`                                                       |
| `tools`   | `packages/tools`   | `domain`                                                       |
| `agents`  | `packages/agents`  | `domain`, `tools`                                              |
| `engine`  | `packages/engine`  | `harness`, `agents`, `tools`, `domain`                         |
| `cli`     | `apps/cli`     | `api`, `web`, `engine`, `store`, `harness`, `tools`, `domain`  |
| `web`     | `apps/web`         | `domain`                                                       |

- The application core is `engine`: a run, from the configuration to the summary, the operations on the sessions of an instance — open one, speak to it, interrupt it, read them, follow one — and those on its configuration — read it, check a change, save one, keep it in step with its file — with no HTTP, no terminal and no SQL in them. The API is their REST presentation: each route calls one operation, and the pipes, the problems and the stream of server-sent events are all it adds. It imports `engine`, `store` and `domain`, and never `agents`, `harness`, `tools` nor `cli`. The `oqas` command is their presentation in a terminal: each command calls one operation, and the arguments, the lines and the exit codes are all it adds. It imports the same three, with `harness` and `tools` for the initialisation of a test repository. To serve the console, `oqas --ui`, it starts the application of `api` in its own process, by the one entry of that package, and finds the built files of `web` by the manifest of that package, of which it imports no code: the REST presentation is written once, and `api` never depends on `cli`.
- The three clients — the console through the API, the command, the conversation — fulfil one contract: the operations `OPERATIONS` of `domain` lists. An operation added there does not compile in the tests of parity of the clients until each says how it offers it, or names it missing with why; see [the operations and their clients](packages/engine/docs/engine.md#the-operations-and-their-clients).
- Whoever hosts the operations calls the engine in its own process, and runs the sessions it opened; the sessions are kept in the database of the instance through the port `domain` declares and `store` implements. Several processes may reach that database, a server and commands in terminals: nothing passes between them but what each writes there, which the others read.
- The database of an instance is assembled in one place, `InstanceDatabase` of `store`, for every process that reaches it: where the database is, how its schema is brought in order, and the store of the sessions on it. The API and the command line both take it from there, and hand its store to the operations of `engine`.
- The database is a setting: `store` has one schema, one series of migrations and one set of statements, and its `openKysely` alone turns a connection URL into the database that runs them, a SQLite file or a PostgreSQL server. No other file of the workspace names a database, but the place where what the two keep differently is converted, and the tests of what only one of them does.
- A run, from the configuration to the summary, lives in `engine` and nowhere else. What hosts it, the operations on sessions of the engine itself, plugs it into its ports and holds none of its steps; what presents the operations, a server or a terminal, holds none either. `engine` depends on no presentation, and only a presentation depends on it; the command line starts the REST presentation rather than writing a second one, and that is all one presentation takes from another.
- What a run says — an entry of its journal, a line of its traces, its state, its exit codes, the folders it writes to, a message of the person — lives in `domain`, under `src/run/`, and so does its translation into the events of a session, under `src/run-thread/`: the packages that write a run and those that read one share them, and none declares them again.
- The life of a session — its states, the commands each state takes and from whom, the refusals — lives in `domain`, under `src/session-life/`, with the port of what keeps the sessions; `store` implements that port and holds the rules under concurrency.
- The configuration of an instance is kept in its database as revisions. Their contract — a revision, how the configuration file stands to the one in force, the refusals — lives in `domain`, under `src/configuration-life/`, with the port of what keeps them, which `store` implements. The operations that keep them in step with the configuration file, `Configuration` of `engine`, are the one place that takes the configuration from that file, or writes it, for a run, a server or a command — the store reads in it only the state folder its database is in; a run reads its configuration through the port `ConfigurationSource`, and the presentations call the operations.
- The domain imports no external module, those of Node.js included, but the ones listed under `external` in its row of the table: `ajv`, which validates the formats against their schemas, and `node:path`. It holds no decorator, of the experimental TypeScript kind or of the standard one.
- The documents uploaded to the knowledge sources of an instance are kept in its database. Their contract — a document, the rules of an upload, the refusals — lives in `domain`, under `src/knowledge-documents/`, with the port of what keeps them, which `store` implements; the operations on them are `KnowledgeDocuments` of `engine`, and a run writes them to its state folder, where the tools read them as they read a folder of the test repository.
- The web console imports the contract of the API, `@open-qa-stack/domain/sessions` — the sessions, the problems, the configuration with its revisions, and the documents of the knowledge sources with the rules of an upload — and nothing else of the domain: that entry imports no module of Node.js, and the console is type-checked with the types of a browser only. An override of the lint configuration on `apps/web/src/` refuses the main entry of the domain.
- What a thread tells is read once, for every presentation: the folding of the events of a session into the steps of its thread, and the grouping of those steps into turns, live in `domain`, under `src/sessions/thread/`, behind the entry a browser reads. The console and the conversation of the command line each give it their words — a `ScriptWording` — and draw what it returns; neither folds nor groups again.
- The conversation of the command line, `oqas` without a command, lives in `apps/cli/src/conversation/`: its screen is a function of a state one reducer gives, and one component alone holds that state and calls the operations on sessions. Ink and its companions are imported there and nowhere else, a test included — the rule `open-qa-stack/confined-imports` refuses them elsewhere — and the folder is reached by one dynamic import, made when the conversation opens: no other command loads what draws it. Its colours, its glyphs and its layout rules are in one module, `palette.ts`.
- The command line reaches the database of the instance itself, and its code is laid out by what it does: `arguments/`, `commands/`, `output/` for what it prints, `sessions/`, `console/`, `project/`, `errors/` and `conversation/`. A command that would reach an instance through its API would live in `src/connected/`, which an override of the lint configuration lets import `domain` only among the packages of the workspace, and no other file of the command line.
- `@github/copilot-sdk` is imported under `packages/harness/src/copilot/` only, by the implementation of the agent runtime, and by no other file, a test included.
- The tests of a package and its `devDependencies` are left out of the table: a test may run a package with the ones that use it, and the private `testing` package holds what the tests share — the test repository and the scripted model of a run among them, for every host of the engine. A test imports nothing from the test folder of another package.

The table lives in `.oxlintrc.json`, as the options of the rule `open-qa-stack/package-boundaries`, which `lint/check-manifests.ts` also reads.

## Commits

A commit is ready when `pnpm check` passes on it. Its message follows [Conventional Commits](https://www.conventionalcommits.org/): a type among `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore` and `revert`, the scope between parentheses when there is one, and a subject of 72 bytes at most, which is 72 characters in ASCII, such as `feat(check): scan the commits of a branch`. A commit is the work of its author: its message carries no `Co-authored-by` or `Generated-by` trailer.

A change has one branch, and a branch one change. What a review or the continuous integration finds is fixed in that branch before it is merged, not by a burst of fix commits on `main` after it.

A pull request is merged by squashing: its commits become one commit of `main`, whose subject follows the convention and ends with the number of the pull request, the whole within the 72 bytes, such as `feat(check): scan the commits of a branch (#12)`.

## Conventions

- What the code names is in English and does not change with the language of a person: a key of the configuration, an identifier, a state, the code of a refusal. What a person reads is a label, translated: the console keeps its labels in `apps/web/src/i18n/` and the conversation of the command line in `apps/cli/src/solo/conversation/i18n/`, one file per language, under the same keys.
- The `.gitignore` of the repository names what the project itself produces. The files of your own tools, an editor, an assistant or an operating system, are left out by your global one, which `git config --global core.excludesFile` names.

## Continuous integration

The pipeline of the repository, in `.github/workflows/`, runs on every pull request and on every commit of `main`; `ci` can also be started by hand. The workflows that verify a change, `ci` and `release`, only read the repository and publish nothing, so they run the same way for a pull request that comes from a fork. Their one secret, the token of the SonarCloud analysis, reaches that step alone, and the step is skipped where the token is absent. The workflow `cla` is the one that writes: it comments on a pull request and records a signature, on the code of `main` and never on that of the pull request. Every action they use is pinned to a commit.

| Workflow | Job | What it verifies |
|---|---|---|
| `ci` | `static`, `tests (1/4)` to `tests (4/4)`, `own tests (check)`, then `check` | The steps of `pnpm check` on a clean clone, the tests in four parts and each package with its own tests at the same time, every job on a machine of its own, then the merge of their coverage in `check`, the job that tells whether the tests pass as a whole; a pull request tests the packages it touches since its base branch, with the Node.js `.nvmrc` names, the dependencies installed from the frozen lockfile and the Chromium the workspace pins, kept in a cache from one run to the next. Then, when the token is there, the SonarCloud analysis of the code and of the coverage of the whole suite, configured by `sonar-project.properties`. |
| `ci` | `hygiene` | `pnpm scan` on every commit the pull request brings, not only its last: the message of each, and the lines it adds. |
| `ci` | `advisories` | No production dependency has a known vulnerability of moderate severity or more. |
| `release` | `candidate` | Started by hand for a version: the check, the scan of the whole history, the advisories, then the tarball of every package, kept as artifacts of the run. It publishes nothing and tags nothing. |
| `cla` | `cla` | Every author of a pull request has signed the [contributor license agreement](CLA.md); the signatures are kept in the branch `cla-signatures`. The maintainer and the bots that open dependency pull requests are exempt. |

A pull request is merged once `check`, `hygiene`, `advisories`, `cla` and the SonarCloud analysis are green. `.github/dependabot.yml` proposes, each week, the updates of the pinned dependencies and those of the actions, each kind in one pull request, so that the pipeline runs once for them.

## Scanning before publishing

`pnpm scan` looks for what must not be published, and changes nothing.

- Without arguments, it scans the files of the index for secrets.
- With revision ranges, as `git log` reads them (`pnpm scan main..HEAD`), or with `--all` for every branch and tag, it also scans the commits they select: the message of each commit, by the rules of the section above, and the lines it adds, for secrets. The lines a merge adds are those its author wrote on top of what git would have merged by itself, which needs git 2.36 or later.

Its rules find a secret by its format: `private-key` a private key in the PEM format, and `github-token` a token in the format of a GitHub token. A finding names the file, the commit when there is one, and the rule, never the secret. The scan ends with `0` when it found nothing, `1` when it found something, and `2` when its arguments or a revision are wrong.
