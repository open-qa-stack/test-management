# Designer

`new Designer(options).run()` writes the Playwright tests a brief needs, as many as it takes, from a brief and the [domain index](../../domain/docs/domain-index.md) of the test repository, on a new local branch, after a test plan. It needs the resolved configuration, the path of the test repository, the environment variables the configuration names, an `AgentRuntime`, a `TestRunner` that runs each test against the application (such as the `TrialRunner` of the harness), and the system instructions of the agent that writes the tests, which the caller composes from the test charter:

```ts
const charter = resolveCharter(config.charter);
const instructions = writerInstructions(charter.rules, config.repository);
const outcome = await new Designer({
  config,
  repositoryRoot,
  env,
  runtime,
  writerInstructions: instructions,
  runner,
  brief: "Test the search of a customer and their profile.",
}).run();
```

`brief` says what to test in the developer's words: a domain, a ticket, a rule, a journey. Without it, the designer works on the whole index. It is given to the agent between `<brief>` tags its own text cannot close. `inbox`, the `Inbox` of the run, lets a person speak to the session that plans and to that of each scenario while they are open, never to a session that reviews for them; what they said is recalled to each of these sessions that opens later, in this design and in the next passes of the run: see [the messages of the person](./cartographer.md#the-messages-of-the-person). `reviewPlan`, `false` by default, has the agent that reviews plans asked about duplicates, in sessions of its own. `planReview`, a `PlanReview` of `@open-qa-stack/domain`, decides whether the test plan may be carried out; by default every plan is accepted as it is.

Two agents share a design, each with its own system instructions, its own tools and its own sessions: one **plans**, with `PLANNER_INSTRUCTIONS`, which hold its method, each step with what ends it, and the rules that cause most refusals of a plan, and nothing of the charter; the other **writes** each test from the sheet of its scenario, with `writerInstructions`, which hold its method and the charter. They may be given different models once the runtime allows it: each session is opened on its own.

The instructions of both end with the language of the tests, `design.testLanguage` of the configuration, English by default: the titles of the scenarios and of the tests, their steps and the intents written in their code are written in it, by `testLanguageRule`. The code, its names included, stays in English, and a text the application shows is quoted as it shows it. The agents that review are not told it: they write no test.

## A run

1. **Test repository.** The path must be the root of a git repository with a commit. No tracked file may be changed, no untracked file may lie outside the state folder (`repository.stateDir`) and the index folder (`repository.indexDir`), and the branch to create must not exist. Otherwise the journal names each problem, no session starts, and nothing is written. The untracked index the cartographer leaves does not stop the run.
2. **Index.** `<indexDir>/domain-index.json` must match its schema. The request of the session that plans gives the agent the brief, then one line per domain of the knowledge, whatever the brief: its identifier, its label, what it is, and how many elements of each kind the sources hold of it, such as `- customers (Customers): The customers of the shop. 2 tables, 1 screen.`. Nothing else of the knowledge is given: the agent explores it by levels (see [The index as a map](#the-index-as-a-map)). Then come the applications, each with how the agent signs in while it explores — with its `fill` tool and the account named, never a credential — and the next call. The rules of a plan are not repeated in it: each is a gate of the harness, told when it refuses, or a line of the system instructions.
3. **Sessions.** A design runs in several sessions, each with tools, watches and limits of its own, and a browser that starts only if the session uses it:
   - **the session that plans.** The agent that plans gets the index tools, the browser tools of the applications of the environment of the index, watched (see [The screens](#the-screens)); the tools of every knowledge source attached to that environment or to none — documents, contracts, bases, source code and logs — the bases read in a read-only transaction, the logs masking the value of every variable the configuration names; the notes, to keep (`remember`) and to read (`recall`); and `propose_plan`. It explores, then submits a test plan (see [The plan](#the-plan)). Once the plan is accepted, the agent is told so, and that its session is over: every later call of a tool is refused with `The plan is accepted, and this session is over. Answer with one sentence; call no more tools.` The session has neither `run_test` nor `propose_test`: no test is run before a plan is accepted;
   - **the session of each scenario**, in the order of the plan (see [Writing each test](#writing-each-test)). It is given the sheet of its scenario and nothing else of the plan, nor anything of the session that planned: its browser opens on the user interface, signed out, and its watches start empty. The agent that writes gets the browser tools of the application of its scenario alone, the tools of the knowledge sources its scenario cites and of those that tell why a run failed, logs and source code, `recall`, `run_test` and `propose_test`; it has neither the index tools, nor `remember`, nor `propose_plan`. Its request says how its test signs in — by the lines of its sheet, which read the account from `process.env`, or, without a user interface, by the variables named — and the packages a test may import, then gives the sheet; it runs the test of the scenario against the application, fixes it, and closes the scenario, every run counting against the limits of the session.

   The limits of the configured autonomy apply to each session, counted afresh. An agent that stops while no plan is accepted, or while its scenario is open, is reminded up to three times, with where it stands — `No plan is accepted yet.`, `The plan was last refused for: <codes>.`, or the scenario open, such as `Scenario 1 of 3, list-orders: its last run failed (1 of 3).`, its test having otherwise `not run` or `passed and is not closed` — and the next call. The search of each base says in its description that a value of the data of a plan comes from a result such as its own.

4. **Branch.** Once the sessions are over, a branch is created from the revision checked out, and stays checked out. The kept tests, the design state and the file of the plan are committed on it with the identity and the hooks of the repository. The message is `test: add <n> generated Playwright tests`, with one line per test: its path and the title of its scenario, or, for a test kept failing, `- <path>: failing (<cause>) at step <n>`, the number of the step its last run failed at, or, for an unfinished one, `- <path>: unfinished (<check>)`. Nothing contacts a remote, and no existing branch nor the git configuration is changed.

The branch is `oqas/design-<date>` by default, such as `oqas/design-20261113T100000Z`; `branch` gives another name.

A design that goes on with an earlier one, such as the next turn of a session, is given its branch as `continuedBranch`: that branch must exist, and no other is created. The design checks it out before it reads anything, when it is not checked out already, so that the agent that plans finds the tests it holds among those of the repository and sets aside what they cover; its tests are then committed on that branch.

## The index as a map

The index tells where to look, without limiting where the agent may look:

- `knowledge_domain` takes a domain. With the domain alone, it gives the sources that hold it, each with its type, the tools of the agent that read it — such as `shop_guide_read_section` for a document — or that no tool of the agent reads it, and how many elements of each kind it holds of the domain, such as `2 tables, 1 view`. With a source too, it gives what that source says of the domain: for a source whose workflow wrote the files of its domains, such as a database, the markdown file of each of its own domains that holds an element of the domain — the role of each table, its columns, its links — cut after 8,000 characters; for any other source, a line per element its card places in the domain. A tool belongs to the knowledge source or the application whose scoped prefix is the longest start of its name.
- `knowledge_list` gives the elements of the knowledge, a line each — its source, its name, the summary of its card and its kind — narrowed by a `kind` (`screen`, `table`, `view`, `operations`, `section`, `folder`), a `domain` or `words`, forty at most, those that echo most words first. An element echoes by its name, the summary of its card and its key fields. Words match without regard to case or accents, a word matching another it begins, or that begins it, when the shorter of the two has four letters or more. When nothing matches, it says so with the kinds of the knowledge: the knowledge is a map, not a limit.
- `knowledge_read` takes a source and one of its elements, and gives the source with the tools that read it, the element with its key fields and the facts of its card, for a table the call that finds one of its rows, the domains it belongs to, and, for a source whose workflow wrote an export, the definition of the element from that export, cut after 8,000 characters.

The tools of a source read the whole source, not only what the index places in it.

## The screens

A test relies on screens the agent saw. The browser tools are those of `@open-qa-stack/tools`, with what the agent needs to see added to their results:

- opening an address returns the snapshot of the page, each element with the locator a test uses for it, without the reference of each element nor the address of each link, which a test has no use for;
- `click`, `fill`, `select_option` and `check` return the lines of the snapshot that appeared after the action (`appeared`), sixty at most, and those that went (`gone`), twenty at most, with a `note` for each value a field holds that the page does not show beside the fields after the action though a line that went showed it, or, for a value the agent typed, though a screen before showed it beside the fields and the action removed a line beside them, the focus aside, as a search filters a list — such as a full name shown on one screen and searched on another whose search matches a first or a last name only; an action that only adds lines, such as one that tells a field is missing, filtered nothing — unless an action before found it, changing what the page showed beside the fields, the focus aside, while a line there showed it — what was searched matched nothing, and a part of it, such as a first or a last name, may, while a row the search found and an action then removed, such as one deleted, is no such value; the note reads `Nothing beside the fields shows "Ada Brennick" now, though a screen showed it: if you searched it, it matched nothing. Try a part of it, such as a first or a last name.`, and the value, exactly as the field held it, since a search may tell the case, counts as searched in vain until an action finds it; a snapshot of a part of the page, taken with `within`, is not what the next action is compared with;
- each of these tools returns in `code` the line a test writes to do the same, as the [browser tools](../../tools/docs/browser-tools.md) give it;
- `goto` and each of these actions return in `action` their number, from 1, in the order they were done, whatever their application, such as `{ "url": "…", "title": "…", "code": "await page.goto(\"/orders\");", "action": 1, "page": "…", "truncated": false }`. The harness keeps each action with its number, its tool, its line of code and the value it typed or chose, when it was given as a text: a plan cites the actions that do its steps (see [The plan](#the-plan));
- each time a snapshot is read, the harness checks on the page, with the browser of the session and without the model, the locator of each element the snapshot gives no locator of its own, for the lines the page did not show before, two hundred at most — by role and exact name for an element with a name, such as a heading or a cell, and by its exact text for an element without one that shows a text, such as a paragraph —: how many elements it designates, and whether the page shows the one it designates. For several, it looks for one of them alone inside the parts of the page that hold the first, the three closest: a part with a name, such as its row or its region, or one told by its role alone, such as its table, a dialog or a form. An element whose locator could not be checked — past that number, or on a page that could not be looked at — is never the element of an expected text;
- the descriptions of `goto` and of the actions say what they return: what the page shows, or what appeared and what went, the line of code, and `"action", its number: a plan cites it in the steps the action does.`

An application without a user interface has no browser tools, and none of what follows that reads the screens applies to it.

## The sources

A plan relies on what the agent read. The tools of the knowledge sources return what they always do; the harness keeps, for each source, every text and number of what its tools returned, each value of the variables the configuration names masked first, up to 200,000 characters, the oldest going first. A call whose result is an error reads nothing. A call of a tool of a source of logs or of source code counts as a look at what a failed run did, and so does a call of a tool of any source for an application without a user interface (see `TEST-LOOK`).

## Refusals

Every refusal of `propose_plan`, `run_test` and `propose_test` gives each reason on a line of its own, which starts with `Refused (<code>):`, then ends with `Nothing else was refused.`: the agent fixes all of them at once. The journal gives each reason with its code first, such as `[PLAN-ID] The plan was refused by the harness: …`, so that a trial is scored by counting codes.

The harness counts, for the plan and for each scenario, how many calls each code refused; the count of a scenario starts again when its test runs. From the third refusal of one code, the agent is told only what that gate would accept, after `Third refusal for the same reason. Do this:` (then `Fourth`, `Fifth`): the skeleton of the scenario for `TEST-ONE` and `TEST-STEPS`; for `TEST-VALUE` and `TEST-POLARITY`, every assertion of each step refused, not only of the texts it misses, so that a model does not drop the others, written as the skeleton writes it (see [Writing each test](#writing-each-test)), such as `Step 2 must hold all of these, with its actions:` then `await expect(page.getByRole("row", { name: "ORD-1042 Mira Veldane" })).toBeVisible();`; for `TEST-ACTION`, the lines of code the plan gives for the step, or, when it gives none, those the browser tools last returned; for `TEST-LOCATOR`, the closest elements the screens showed; for `PLAN-DATA`, the tool that reads the source and the last five texts it returned; for `PLAN-SHOWN` of a value the scenario invents that no field held, to type it and expect what the screen answered, with the last line of code that filled a field; for any other code, its first refusal alone. The fifth refusal of one code closes the scenario, and the journal records it as an error. When a run of its test gave a verdict, the text of the last such run is kept as it ended: passed, or failing with the cause `test` and the evidence `closed by the harness after 5 refusals for <code>`, the state giving the code in `closedBy`; the agent is told `Scenario <id> was closed by the harness after 5 refusals for <code>, with the test of its last run: <outcome>.` Otherwise its test is kept as unfinished (see [Design state](#design-state)): the agent is told `Scenario <id> was closed by the harness after 5 refusals for <code>; its test is kept as unfinished.` Either way its session is over. The sixth plan the gates refuse stops the design, as a plan the review refuses does. A plan refused that comes again with the same scenarios and no browser action since is told so once, before its refusals: the same refusals hold, and the agent does what they name or leaves the scenarios out in `uncovered`. Texts a scenario makes go at the same step are told in one refusal.

A text is observed in what the tools returned when, its spaces collapsed and its case aside, it is part of one of their texts; a text shorter than three characters is not checked.

## The plan

No test is run before a plan is accepted: the session that plans has neither `run_test` nor `propose_test`. `propose_plan` takes as many scenarios as the brief needs, each verifying something the others do not — one per business rule, information or behaviour the brief is about; each test carries out one of them. The scenarios are submitted in several calls, and the harness sets aside the duplicates: see [the scenarios of a plan, asked until the brief is covered](#the-scenarios-of-a-plan-asked-until-the-brief-is-covered). A scenario has:

- a slug of its own (`id`), which names the file of its test, a `title` and its `intent`;
- its `kind` — `functional`, `visual`, `accessibility` or `other` — and its `case`: `negative` when the input matches nothing, is wrong or is forbidden, `nominal` otherwise;
- the one `application` it is about, and the `domain` of the index it comes from;
- the `sources` it relies on, each a source and, when one is named, an element of it; a source is a knowledge source of the environment or an application, whether the index lists it or not;
- its `data`: each value its test enters, with the source or the application whose tool showed it, or `made-up` for a value it invents;
- its `steps`, one to eight, each an `action` of the user, in `actions` the numbers of the actions of the exploration that did it, in the order a test does them, as the results of the browser tools gave them — none for an application without a user interface; scenarios may cite the same actions, such as those that sign in — and zero to four `expects`, each a `result` in one sentence with the exact texts the screen then `shows` and those it no longer shows (`absent`).

The agent writes neither a line of code nor a locator. Once the gates passed, the harness inscribes the plan: each step gets in `code`, in place of `actions`, the lines of code of the actions it cites, in the order cited; each expect gets in `elements` the element the screens showed each of its texts in — its `text`, its `locator`, and whether it is a `field`, which holds the text as its value — as the skeleton of a test found it before (see [Writing each test](#writing-each-test)). A text no screen showed in an element has no entry: its test finds it by its text. So has a part of the text of an element, which a snapshot gives on a line of the role `text`, such as a sentence of a paragraph that also holds a button: no element shows it whole, and a locator by its exact text would find none. The plan reviewed, kept and written to its file is the inscribed one.

The element of a text comes from the screen of its step alone: for a text expected shown, what the page showed between the last action the step cites and the next action; for a text expected gone, what the actions of the step removed, then any screen seen. A text another screen showed in an element — the same name in a row of a list and in the heading of a profile — is never given the element of that other screen. The locator of each element was checked on the page while the screen showed its line (see [The screens](#the-screens)). The harness takes first an element whose locator designated it alone. Failing one:

- an element whose locator designated nothing the page showed is an error, `PLAN-ELEMENT`;
- an element several share the locator of is asked about, once, in a result of `propose_plan` that is no refusal and starts with `The plan is not accepted yet.`: a **proposal**, numbered, when the harness found the locator of one of them alone, which the agent checks, such as `Proposal 2: "Due" (scenario list-orders, expect 1.1) is shown by 2 elements of shop. The harness proposes to assert it on one of them alone: page.getByRole("region", { name: "Late orders" }).getByRole("heading", { name: "Due", exact: true }). Check that it is the element you mean: if it is, put 2 in accepts. Otherwise expect a more precise text, such as the text of the whole row.`; a **warning**, numbered, when it found none, which the agent confirms when any of the elements will do.

The agent submits the plan again with, in `accepts`, the numbers it accepts. A proposal accepted is inscribed with the locator proposed. A warning accepted, and whatever was left unanswered, is inscribed with the locator they share and their number, `count`: its assertion holds for any of them. Nothing is asked twice, the journal records each question and how it was settled, and a result that asks counts as no refused plan. The actions a scenario of an application without a user interface cites are left out.

The harness numbers the steps from 1, and the expects of step `n` from `n.1`. A source without any tool is held to none of the gates that read it, and a text or a value shorter than three characters is not checked.

Before its gates, the harness takes out of a functional scenario of an application with a user interface what a field only echoes: in a step whose action types — as `PLAN-INPUT` reads it — without joining another action with `and` or `then`, and that another step follows, each text it `shows` that is, spaces and case aside, a value of the data of the scenario that no screen showed beside the fields. The field holds the value whatever the application answers, so that the result is what a later step expects. A text a line beside the fields showed, such as the cell of the row a search found, is what the application answered, and stays. The gates number the expects as the agent wrote them, and pass over one the harness left without a text; the plan reviewed and kept goes without it. The harness does not do it behind the back of the agent: once the plan is accepted, the result of `propose_plan` tells each text taken out, and the journal records it, such as `The harness took "Quill Zed" out of expect 2.1 of scenario search-unknown-customer: the field echoes what the step types.` The last step, and one that types and sends, keep what they show: the application may answer with the value, such as the row of a customer it saved.

The refusal says to put the text in `shows`, to make the scenario negative, or, when a step removes it, to show it in the step before, and, when the screens found nothing, to try a part of the value, such as a first or a last name. A nominal scenario whose steps type is refused too when a value it types is one the screens searched in vain, as the `note` of an action told it: a nominal scenario finds what it searches. A scenario types the values of its data that the actions of its typing steps name, or, when they name none, each value of its data a field held; a value it only clicks, such as the name of the row it opens, is not typed. The refusal says to replace the value, in data and in the step that types it, by a part of it, such as a first or a last name, that the `fill` tool of the application searched and found, and to expect what it found, or to make the scenario negative.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `PLAN-LEVEL`    | The level of a scenario does not fit what its cited actions went through, or is none of those asked: a `smoke` test that does more than open an address, a `functional` one whose actions went through several screens, a `business` one that stayed on one. The refusal names the screens, by their route, and the level that fits when the plan is asked for it; when it is not, the refusal asks to leave the scenario out and to say in `uncovered` the level it needs, and never suggests a level the plan is not asked for. |
| `PLAN-LOCATOR`  | For an application with a user interface, a step cites no action, an action no browser tool returned in the session, or one done on another application: the harness could write no code for it. The refusal names the step and says to do it with the browser tools of the application and to give the numbers their results return in `action`, such as `"actions": [3, 4]`; from the third, it lists the last ten actions done on the application, each after its number, such as `2: await page.goto("/orders");`, An application nothing was done on is told once, whatever the number of its scenarios and of their steps: `you did nothing on the screens of shop in this session, and the scenarios a, b, c are about it: …`, with what to do.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `PLAN-START`    | For an application with a user interface, the first action the first step of a scenario cites opens no address: its test starts on an empty page. The refusal gives that action and says to open the first address of the scenario with the `goto` tool, to do the steps from there, and to cite that action first, with the last action that opened an address as an example.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `PLAN-SIGNIN`   | A scenario of a level above smoke acts on an application after the agent signed in to it, and none of its steps cites the actions that signed in: a test starts signed out. The refusal names those actions — the address opened before the credentials, the credentials, and the action that sent them — and says to cite them first in the first step that acts on the application, or to do the steps again signed out for a scenario that verifies what a person who is not signed in sees. |
| `PLAN-ELEMENT`  | The only element the screens showed an expected text in has a locator that designated nothing the page showed when the harness looked for it: no element, or one the page hid. The refusal names the text and the locator, and says to take a snapshot of the screen that shows the text and to expect a text as one of its lines gives it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |

The sixth plan the gates refuse stops the design (see [Refusals](#refusals)). A plan that keeps these rules goes to `planReview`, one plan at a time. Accepted, it is frozen and kept in a file the design state names (see [The file of the plan](#the-file-of-the-plan)), no other may be submitted, and the agent is told `The plan was accepted.`, what the harness took out of it, then `Next: answer with one sentence. Call no more tools.`: the session that plans is over. Refused, the journal gives the reason, every later call of the agent, whatever its tool, is refused, the agent is not reminded, and the design fails without writing any test or creating any branch. The brief is written to the state and to the file of the plan as it was given.

## Writing each test

The scenarios are opened one at a time, in the order of the plan; the agent never names one, nor a file. The test of a scenario goes to `<appsDir>/<application>/<id>.spec.ts`, or `<id>-2.spec.ts`, `<id>-3.spec.ts`… when a file of the repository already has that path; nothing is written in the blocks nor the journeys folders.

Each scenario is written in a session of its own. Until its session begins, and once the scenario is closed, `run_test` and `propose_test` are refused with `SCENARIO-CLOSED`: `the scenario of this session is closed. Answer with one sentence; call no more tools.`

The sheet of a scenario, which the request of its session ends with, gives its rank in the plan, its id, title, kind, case and application, its intent, its data, the elements of the sources it cites, its file, then the skeleton of its test, then the next call:

```text
Scenario 1 of 3: search-order-by-customer — Search an order by customer name (functional, nominal), application shop.
Intent: Verifies that a search by last name finds the orders of the customer.
Data: "Veldane" (shop-db).
Cited: shop-db: public.orders.
File: apps/shop/search-order-by-customer.spec.ts

import { expect, test } from "@playwright/test";

test("Search an order by customer name", async ({ page }, testInfo) => {
  await test.step("1. Search the orders of Veldane", async () => {
    await page.goto("/orders");
    await page.getByRole("textbox", { name: "Search orders", exact: true }).fill("Veldane");
    await page.getByRole("button", { name: "Search", exact: true }).click();
    // Expect 1.1: The search lists the order of Mira Veldane only.
    await expect(page.getByRole("textbox", { name: "Search orders", exact: true })).toHaveValue("Veldane");
    await expect(page.getByRole("cell", { name: "ORD-1042", exact: true })).toBeVisible();
    await expect(page.getByText("ORD-1057")).toBeHidden();
    await testInfo.attach("1", { body: await page.screenshot(), contentType: "image/png" });
  });
});

Next: check the skeleton of search-order-by-customer against its steps, complete what a comment asks, then call run_test with the whole file.
```

The skeleton parses and keeps the default charter and the gates below as it is: one `test.step` per step of the plan, titled by its number then its action, with the lines of code the plan gives for it — or, for a step the plan gives no code for, such as one of an application without a user interface, the comment `// Do: <action>. Copy the code lines the browser tools returned.` — and an assertion of each text of its expects, on the element the plan gives for it. The harness found that element when it inscribed the plan, on the screen of the step, the last seen first: the element named by the text, by its locator in the snapshot or by its role and name, or the element without a name that shows the text and nothing else, such as a paragraph, by its exact text (`toBeVisible`); else an element whose line holds the text and gives its locator (`toBeVisible` when the locator names the text, `toContainText` otherwise); else the field whose value is the text (`toHaveValue`), a field holding what the agent typed whatever the application answers; else the text itself (`getByText`), which the harness could count nowhere and the page may hold in several places: one a user sees is enough, `await expect(page.getByText(<text>).filter({ visible: true })).not.toHaveCount(0);`. That last form is the weakest, kept for what nothing else finds: an element the page holds hidden is none. A text expected gone is looked for first in the lines the actions of its step removed, never in a field, and asserted `toBeHidden()`. A text on an element several share the locator of is asserted by their number, without any position: `await expect(<locator>.filter({ visible: true })).not.toHaveCount(0);` for one the screen shows, `await expect(<locator>).toHaveCount(0);` for one it no longer shows. The agent may find its element better, never change the text. The screenshot of each step is there when the `screenshots` option says so, as the solo command does while the rule `PW-SHOT-01` of the charter is active.

`run_test` takes the whole text of the file, checks it, then runs it against the application. The checks come in tiers; the first tier that refuses gives all its reasons, and a text refused is not run:

The message of an `expect` holds no text, nor does a statement whose subject chains `.or(…)`, which may pass on the other element.                                                                                                                                                                                                 |
| 3    | `TEST-POLARITY`   | A text the screen `shows` is held only by negative statements — `.not`, `toBeHidden`, `toHaveCount(0)` — or a text it no longer shows only by affirmative ones.                                                                                                                                                                                                                                                                                                                                                                                                                                        |

| 3    | `TEST-LOCATOR`    | The test uses a locator by role, text, label, placeholder, test id, title or alternative text that is none of the skeleton of its scenario — the same role and the same name or text, which the plan gives — and that no snapshot of the session showed: the role at the start of a line, and the name or the text observed in a line, the same or another — the name of a row is that of its cells. Example: …`.                                                                                                                                                                                                                                                                                 |

A text the checks accept is run with the `runner` option, a `TestRunner` such as the `TrialRunner` of the harness. The agent is told the verdict of each of its tests and, for one that did not pass, its error, cut past 1,500 characters, the `test.step` that failed, the path of its trace, and the instant from which the logs of the services tell what happened; then one hint, picked by what the run stopped on, after, for a test that types no credential of an account and failed on a page that asks for a password, that it starts signed out and must sign in at its first step; when the runner gave the page at the failure, the elements of that page that held each text the step that failed expects shown, beside the fields, three at most, and the texts it showed nowhere; and how many runs of the scenario failed, out of three; then the next call. The lines of the page at the failure count as lines the screens showed, so that a test may find an element of it. A run that could not happen, or gave no verdict, counts as failed.

A test writes no file. A visual test compares a page with its reference, with `toHaveScreenshot`; its references are made at its first run, committed with the test, and listed in the design state.

`propose_test` closes the scenario open with the text of its last run that gave a verdict, which is not run again; the agent is told how it ended, such as `Scenario list-orders closed: passed.`, then `Next: answer with one sentence. Call no more tools.`: its session is over, and the next scenario is written in another. The calls of `run_test` and `propose_test` run one after the other, even those of one turn, each seeing the run the previous one recorded. It is refused when:

| Code             | Cause                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PROPOSE-RUN`    | The test of the scenario has not run, or its last run gave no verdict — it could not run, or was `not_run`, `skipped` or `blocked` — and fewer than three of its runs failed. With three, the scenario is closed with its last run that gave a verdict, under the rules below, or, when none did, with its test kept as unfinished (`TEST-STOP`), which the journal says.                                                                                                                                                                                                                    |
| `PROPOSE-DIAG`   | The last run failed, and no `diagnosis` is given.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `PROPOSE-EARLY`  | The cause is `test`, and fewer than three runs failed: the test is repaired first, or closed `unfeasible` when nothing in it can get past the failure.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `PROPOSE-CAUSE`  | The cause is `application` or `plan`, and the last run did not fail on an assertion: it stopped before any check of the application; or its assertion found no element, and the page at the failure showed, beside the fields, each text the step that failed expects shown that the error names, and none that the step expects gone: the assertion looked in another element, and the refusal gives an assertion on the element that held the first. A matcher of the page, such as `toHaveURL`, or one that found its element, such as a negative one, says nothing of where the text is. |
| `PROPOSE-SECRET` | The evidence of the diagnosis holds a secret of the configuration, a connection string or the key of the model. |
| `PROPOSE-UNFEASIBLE` | The agent gives the scenario up with `unfeasible` and its reason: no test can do what the scenario asks. A warning the first time, since the scenario then has no test — the same call again confirms it; a refusal when its test passed. |
| `PROPOSE-CONFIRM` | A warning, told once per scenario: the cause is `application` or `plan` while runs are left. The plan was accepted on what the application showed when its steps were done, so the agent is asked to compare the test with the plan and repair it; the same call again confirms the diagnosis. |

Every refusal leaves a way out: a run that fails again counts, a scenario with three failed runs may be closed with the cause `test`, or is closed with its test kept as unfinished when none of its runs gave a verdict, and a scenario refused five times for one reason is closed by the harness, its test kept as its last run that gave a verdict ended, or as unfinished.

The harness journals what the session of a scenario looks at beyond its sheet: each call of a browser tool or of a tool of a source is an entry `[SHEET-BEYOND] Scenario <id>, before any failed run: <tool>.` or `… after failed run <n>: <tool>.`, and the session ends with `Scenario <id>: <n> calls beyond its sheet.`, even for none. Doing again an action of the sheet — the tool returns a line of code the sheet gives — is no such look. A look before any failed run is a gap of the plan, which left the writer something to find; a look after a failed run is the one a repair needs.

A plan covers its brief: each business rule, each information and each behaviour the brief is about has a scenario that verifies it, and the instructions of the agent that plans say so. What no scenario covers is said, never left out in silence. A brief may ask what the application does not let a test do, such as an action no screen offers. The agent that plans says so in `uncovered` of `propose_plan`, each entry with what the brief `asked` and the `reason` — what it saw of the application or read of its sources, or that the plan has no room for it — in as many words as it takes, rather than plan a neighbouring test in its place without a word. The harness keeps it with the plan, writes it in the file of the plan under the heading `Not covered`, journals it as an error — `The plan does not cover what the brief asks: …` — and gives it in the outcome of the design, so that the command prints it. It holds no secret, as the rest of the plan.

### The review of a test for coherence

A rule of the harness measures the steps of a test, their titles, the texts expected and the locators. Whether the test verifies what its scenario means is a matter of meaning, asked of an agent of its own: the coherence reviewer, in a session of its own, with the scenario, the test and `report_findings` as its only tool. It sees nothing of the session of the agent that wrote the test, reviews neither duplicates nor the quality of the code, and is told that a doubt is no finding.

With the option `reviewTests` (the key `design.reviewTests` of the configuration, `true` by default), a test that passed is reviewed when its scenario is closed:

| What the reviewer says | What the harness does |
|---|---|
| Nothing | The test is kept, with its review. |
| Findings, five at most, each a place and a sentence | They are told once to the agent that wrote the test, as the warning `TEST-COHERENCE`. It repairs the test and runs it again, or proposes it again as it is. |
| Findings again, on a text repaired or kept | The test is kept as passed, with the findings, for a person to decide: nothing is told twice. |
| No answer: its session failed, reached a limit or ended without a report | The journal says so, and the test is kept without a review. |

The reviewer refuses no test alone. Its last review is kept with the test in the design state, as `review`: its date and its findings, none when the test is coherent with its scenario. A text is reviewed once: proposed again unchanged, it is not read again.

### The reference of Playwright

The agent that writes a test and the agent that reviews its code are held to the Playwright the tests run with, not to the one they remember. Both get `playwright_search` and `playwright_read`, the [tools that read the reference](../../tools/docs/knowledge-tools.md#the-reference-of-playwright) of its API in the packages the test repository installs: what a method does, how it is declared and each of its options, at that very version. A member the reference does not have does not exist there. The reviewer is told to read a method before it says one does not exist or names one to write instead; the agent that plans writes no code, and has neither tool.

### The review of the code of a test

A third agent reviews the quality of the code, whatever the plan: the code reviewer, in a session of its own, with the test and `report_quality` as its only tool. Its instructions are composed from the test charter by the caller, as those of the agent that writes are — `reviewerInstructions` of the harness —, and the review is done when the option `reviewCode` of the designer asks for it: the command asks unless the key `design.reviewCode` of the configuration is `false`.

It is told what is fixed and is no finding — what the harness writes from the plan: the title and the tags, the steps and their titles, the comments of the expects, the screenshots, the locators, the texts asserted and the values typed — and what it reviews: a rule of the charter the test breaks, which it cites, code that hides a failure, code that does nothing or twice, code a person reads badly. Each finding says what it concerns:

| A finding concerns | What the harness does with it |
|---|---|
| `test` | It is told once to the agent that wrote the test, as the warning `TEST-QUALITY`, with the rule it breaks when it names one. The agent repairs the test and runs it again, or proposes it again as it is. |
| `plan` | It is not told to that agent, which cannot change what its plan fixed: a value asserted that changes with time or with the data of the environment, such as a date or a count of rows. It is kept for a person. |

The two reviews of a test run one after the other when its scenario is closed, coherence first, and what both found is told in one warning. The last review of the code is kept with the test in the design state, as `quality`: its date and every finding, those of the plan included. As the review of coherence, it refuses no test alone, reviews a text once, and is left out, the journal saying so, when its session fails.

### Every scenario accounted for

The agent that writes a test may find that no test can do what its scenario asks: a step the application does not offer once tried, an environment that does not allow it. It says so with `propose_test` and `unfeasible`, with its reason, rather than force a test. The scenario is then classed `unfeasible`, by the agent, with the reason and the date, and its last text is kept in the state; it is not run.

The harness, not an agent, counts once the sessions are over: each scenario of the plan has a test that counts — passed, or failing because of the application —, or is a duplicate of another test, or was given up with its reason. A design succeeds when the count is right, and the journal names each scenario given up with why. A scenario left without any of the three — its session ended, its runs gave no verdict, its test fails by its own fault — makes the design fail, as before.

### The pyramid of tests

Each scenario has a `level`, its place in the pyramid of tests, and the request of the session that plans names the levels asked, those of the key `design.levels` of the configuration:

| Level | What a test of it verifies | What the harness holds it to |
|---|---|---|
| `smoke` | The application answers. | Its actions only open an address. |
| `functional` | One behaviour of one screen, a scenario each. | Its actions stay on one screen. |
| `business` | A whole journey ends as it must. | Its actions go through two screens or more. |
| `cross-application` | An action in one application has its effect in another. | Its actions were done on two applications. |
| `end-to-end` | A journey goes through three applications or more. | Its actions were done on three applications or more. |

A screen is told by its route, as the browser tools say where the page is after an action: `/customers/:id` for the page of any customer. When the harness asks what the brief still needs, it names the levels asked that no scenario kept is of.

A test of one of the two upper levels acts on several applications. Its scenario still names one `application`, that of its folder and of its base address; the harness reads the others from the actions it cites and writes them in the plan as `applications`. Such a test opens a tab for each other application, in the same browser context, as the exploration has a page for each: what is under way on one stays as it is while the test acts on another. The skeleton opens the tabs (`const deskPage = await context.newPage();`), the lines of code of the actions done on another application act on its tab, and an address is opened there on the base address the runner gives for the application, such as `await deskPage.goto(new URL("/tickets", process.env.OQAS_BASE_URL_DESK).href);`. A tab is empty until an address is opened on it: the first action cited on another application opens one (`PLAN-START` otherwise), and the test comes back to a tab without opening it again. A step is of the application its last cited action was done on, and its expects are asserted on that tab. The screens of all its applications are taken as one: an expected text may come from any of them, and the session that writes its test has the browser tools of each. A scenario of a lower level that cites an action of another application is refused as before.

### What a test does to the data

Each scenario says its `effect`: `read` when its test only reads the data of the environment, `write` when it creates, changes or removes some. Every test and every user share that data, so a test that writes must pass again right after it passed: it enters data of its own, such as a made-up name no other run uses, or its last step puts back what it changed.

- **In the plan.** A scenario said to only read that cites a click that writes is refused with `PLAN-EFFECT`. A click writes when the page sent, while it was done, a request of the method `POST`, `PUT`, `PATCH` or `DELETE`, as the network tool of the application lists them: a click that only opens a dialog, such as one on *Respond*, writes nothing, and one that sends a form writes whatever its name. For an application whose requests cannot be read, the harness falls back on the guess from the words of the name that guards an exploration.
- **In the plan, again.** A scenario that writes, finds a text before it writes anything, expects it gone at a later step and never expects it shown again removes what it starts from: it is refused with `PLAN-EFFECT`, and asked for a last step that puts the text back, done on the screens too, or for data of its own.
- **On the screens.** Before it keeps a scenario that writes, the harness looks by itself: it opens again the address the scenario starts on and reads the page, without the look counting as one of the agent. When the page no longer shows a text the first step finds there, the exploration changed the environment and did not put it back: the plan is refused with `PLAN-EFFECT`, the journal says what the harness saw, and the agent is told to put it back on the screens, or to start the scenario from what the page shows now. Only a first step that opens addresses and nothing else is looked at; a page that cannot be read holds the plan to nothing, and so does an application the agent signed in to: the harness reads the page in the browser of the agent, signed in, and a test starts signed out.
- **In the run.** A test that writes is run a second time once it passed. When the second run fails or cannot run, the test is held to have failed, and the agent is told why: it relies on data its own run changed.
- **In the tags.** `@data-read` or `@data-write`, so that a run of the tests that only read is one command away, such as `--grep @data-read`.

The harness writes on each test the tags of its scenario, after its title: `@level-functional`, `@domain-customers`, `@app-policy-management`, `@kind-functional`, `@case-negative`, `@data-read`, with one `@app-…` for each application a test of several acts on. They are in the skeleton, and the harness writes them again on every text the agent submits, in place of any it gave: a run selects tests by them, such as `--grep @level-smoke`. They say nothing of what a test does, and two tests that differ by them alone are one test.

### The scenarios of a plan, asked until the brief is covered

A plan is not closed by its first call. Once the scenarios of a call pass the gates, the harness keeps them and answers with a result that is no refusal: the scenarios kept, and the question of what the brief still needs. The agent then calls `propose_plan` with only the scenarios to add — one that bears the slug of a scenario kept replaces it — or with `"scenarios": []` once every case of the brief has its scenario, which closes the plan. Its instructions say so from the start.

Each scenario submitted passes two guards against duplicates, in order:

1. **By the code.** The harness compares what the test of the scenario would do with each scenario kept, whatever their titles and intents: the same application, the same values entered, the same steps — the lines of code of the actions each cites, or its sentence when it cites none — and no text expected that the other does not expect at the same step. Such a scenario is set aside with the check `PLAN-DUPLICATE`.
2. **By the agent that reviews the plan**, when `design.reviewPlan` of the configuration is not `false`. It is an agent of its own, `PlanReviewer`: each review runs in a session of its own, with its own instructions and `report_duplicates` as its only tool, given the scenarios as the harness describes them and nothing of the session that plans. It is asked about the scenarios the code let through. The harness keeps of its report only what names a scenario submitted and a scenario before it, and goes on without it when its session fails. Its lines of the trace bear the phase `review`.

A scenario set aside is never lost: the plan keeps it in `setAside`, with the scenario that covers it, who decided — `{ "by": "harness", "check": "PLAN-DUPLICATE" }` or `{ "by": "agent", "role": "plan-reviewer" }` — why and when; the journal says it, the agent is told it, and the file of the plan lists it under `Set aside`.

The harness stops asking, and the plan records why in `ended`:

| `ended` | When |
| --- | --- |
| `covered` | The agent called `propose_plan` with no scenario: it says the brief is covered. A plan whose functional scenarios are all of what works is asked once, before it is closed, what the application answers to an input that matches nothing, is wrong or is forbidden, and what else a user does on the same screens; the same call again confirms that the brief asks nothing of the kind. |
| `exhausted` | Three scenarios submitted in a row were duplicates. The first is only told to the agent; at the second, the agent is reminded that it may say the brief is covered; the third closes the plan. A scenario kept in between starts the count again. |
| `session-end` | The session of the agent ended once it was asked for more: the plan is closed with the scenarios kept. |
| `refused` | Six calls in a row were refused by the gates while the plan held scenarios: it is closed with them, and the journal says so. A call the gates let through starts the count again. With no scenario kept, the design stops, as before. |
| `none` | The first calls gave no scenario, and said in `uncovered` why no test can do what the brief asks. The first such call is asked, once, to plan the applications one at a time — a brief about several of them is often too broad to plan at once —, and the same call again confirms it: the plan is closed without a scenario, no test is written, and the design succeeds. Without `uncovered`, such a call is refused with `PLAN-COUNT`. |

The plan closed is then inscribed and goes to the review that accepts or refuses it.

Whether a test does what its plan says is another matter, for another agent, which reviews code. The session that writes a test only gets a reminder: a test that passes and runs what the test of a scenario closed before runs — the same body once its titles, its comments and its layout are taken out — is asked about once, in a result that starts with `Warning (TEST-DUPLICATE)`; the agent checks it against its sheet. Closed again as it is, it is kept, classed `duplicate`, with the path of the test it duplicates in `duplicates`: it stays on the branch, is not run with the others, and its scenario is no longer one the design must give a test for.

No test is lost. A session that ends while its scenario is open — the agent stopped, and was reminded three times in vain — makes the harness close the scenario (`SESSION-END`): its test is kept as passed when its last run passed, the agent having only left it open, and as unfinished otherwise. An unfinished test is a file like the others, at the path of its scenario: the last text the agent submitted to `run_test` that held nothing a test may not hold — it parsed, imported nothing forbidden, wrote no file, and held neither an address nor the value of a variable of the configuration — or the skeleton of the scenario when there was none. It does not count towards the three tests a design expects.

A test whose last run passed is kept as passed, whatever the diagnosis says. One whose last run failed is kept unchanged, as failing, with the `cause` of the diagnosis — `application` when the application does not do what the plan expects, `plan` when an expected text of the plan is wrong, `test` when the test could not be made to work — its `evidence`: what the run showed and what the agent checked, and the step and the class its last run failed on. The verdict is always the harness's. A test kept failing counts towards the three a design expects only when the application is at fault.

Every value of the variables the configuration names is masked in the journal and in what the agent is told.

## Repairing tests

A brief that asks to fix tests the repository has is a repair, not a plan. The agent that plans calls `repair_tests` with their paths instead of `propose_plan`, and its session is over. Only a test a design wrote can be repaired: the plan of that design gives the scenario its repair keeps to. The harness refuses a path that is no test of the repository (`REPAIR-UNKNOWN`), a test no plan records, such as one written by hand (`REPAIR-UNPLANNED`), two tests of scenarios of the same name from different plans (`REPAIR-SAME-SCENARIO`), and a repair once scenarios of a plan were submitted (`REPAIR-PLANNED`): a design plans new tests or repairs those that exist, not both.

Each test is then written as the test of a scenario is, in a session of its own, with one difference: its file is the one it has, and the session is first given its text, to run as it is before it changes anything. The harness holds to it: until that text is submitted, `run_test` refuses any other (`REPAIR-AS-IS`), so that the agent sees how the test fails rather than leave out what fails. The run replaces the file for its time, then puts it back. The session is given no skeleton: the test of the repository is its starting point, and what the plan of its scenario gives is told beside it. A repair that does not pass — set aside as unfeasible, or closed by the harness — leaves the file as the repository has it; what was tried is in its runs. The gates, the runs, the diagnosis and the verdict are those of any test; the test is committed on the branch in its own file, and the state of the design records it. A repair is the whole design: no pass follows it, visual or of another level.

## Design state

The state is written to `<stateDir>/designs/design-<date>.json`, and committed with the tests unless git ignores it. It holds the brief, when one was given, the path of the file of the plan accepted, and the test of each scenario closed, in the order of the plan, with the scenario it carries out, the `verdict` of the run of its text — `not_run` for an unfinished test whose text gave no verdict — and each of its runs, with its verdict and, for one that failed, its class and its step. `closedBy` gives the check the harness closed its scenario on, when it did: the code that refused it five times, `TEST-STOP`, or `SESSION-END`. The application, the domain and the reason of a test are those of its scenario.

Each test is classed, in `classes`, a list of dated entries whose last one is how the test stands. An entry gives when (`at`), the `class`, who classed it (`origin`) and why (`reason`):

| Class                                                 | When                                                             | Origin                                                                                                                                                                                                                                |
| ----------------------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `passed`                                              | Its last run passed.                                             | The harness, with the check that decided: `run_test`, the code that refused five times after it, or `SESSION-END`.                                                                                                                    |
| `failing-application`, `failing-plan`, `failing-test` | Its last run failed, and it is kept failing, by who is at fault. | The agent that wrote it (`{ "by": "agent", "role": "writer" }`), the reason being its evidence; or the harness, for `failing-test`, with the code that refused five times.                                                            |
| `duplicate`                                           | It passes, and runs what the test of another scenario runs.      | The harness, with the check `TEST-DUPLICATE`, once the agent that wrote it was warned and kept it as it is. |
| `unfinished`                                          | Its scenario was closed before its test was made to end.         | The harness, with the check: the code that refused five times, `TEST-STOP` or `SESSION-END`. The reason says why, then what was tried: the runs, each with how it ended, and the codes that refused a call, each with how many times. |

## The file of the plan

The plan accepted is written with the state, to `<stateDir>/designs/design-<date>.plan.md`, and committed with it unless git ignores it. It is a Markdown page a person reads, then, under the heading `Record`, a `json` block the harness reads again: `formatVersion`, the identifier of the `design`, its `environment`, its `brief` when one was given, and the `scenarios` as the plan keeps them, with the `code` of each step and the `elements` of each expect. The page gives the same plan, each text on one line: the scenarios in their order, each with its intent, its sources and its data, then its steps, each with the lines of code that do it, the results it expects and the texts the screen shows or no longer shows, each with where a test finds it: `in` the element the plan gives, `in any of the <n>` elements that share its locator, `as the value of` a field, or `by its text` when the plan gives no element:

## Outcome

The sessions are traced in `<stateDir>/traces/design-<environment>-<date>.jsonl`, in the format of the [trace of a cartography](./cartographer.md), with one phase per session: `plan`, then `write` once for each scenario written; the sessions of the agent that reviews the plan write their lines under `review`. A phase holds the request and each reminder, every reasoning, text and tool call of the agent with its result, each entry of the journal written meanwhile, what the session asked of the model (`usage`), and how it ended — `done` when the session gave what it was for, a plan accepted or a scenario the agent closed, `truncated` when a limit cut it, `failed` otherwise. A `person` line is a message of the person delivered to the session of the phase, written once: a message recalled to a later session is read in its request, and has no line of its own. Each line is handed to `observe` as it is written. A design stopped before its first session writes no trace.

`run()` returns `ok`, true when each scenario of the plan has a test that passed or fails because of the application, those whose test is classed `duplicate` set apart; the path of the trace, when a session started; the branch, when tests were written, and the paths of the state and of the file of the plan, when they were written; the tests; `stoppedBy`, the limit that cut the design short, when one stopped the session that plans before its plan, or the session of a scenario while it was open; and the journal, as `{ level, message }` entries.

- With fewer such tests than scenarios, those kept are written and committed all the same, the unfinished ones included, and the journal gives their number.
- With none, nothing is written and no branch is created, unless a limit stopped the design after its plan was accepted: the state and the file of the plan are then written, and nothing is committed.
- When the plan is refused, by the review or six times by the gates, nothing is written and no branch is created; the journal gives the reason.
- When a limit of the autonomy stops the session of a scenario while it is open, the journal names the limit, and the design stops there: the tests of the scenarios closed before it are written, and the scenario under way is not. A limit that stops a session once its scenario is closed, or the session that plans once its plan is accepted, stops nothing: the design goes on with the next session.
- When a session fails, the design stops, and what was kept is written.

The designer runs each test with `runner`, which gives the verdict; the review of the branch judges them.
