# @open-qa-stack/web

The console of an instance: a React application built with Vite. As a rule of the workspace, it may import no package of the workspace other than `@open-qa-stack/domain`, and of it only the contract of its API, `@open-qa-stack/domain/sessions` — the sessions, and the configuration — : the rest of the domain runs on Node.js.

The console shows the agents at work, live. It holds no sample data: everything it shows comes from the API of its instance, [`@open-qa-stack/api`](../api/README.md). Its first screen takes a request, which opens a session, and lists the sessions, the one whose agents are working first; the thread of a session fills event by event, and a session that ended can be replayed step by step. [The configuration](#the-configuration) of the project is shown, changed and saved in a screen of its own. The other parts of the console are named in its navigation as “soon”, and open nothing yet.

## Build and run

From the root of the workspace:

| Command                                  | What it does                                                                                                                     |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm --filter @open-qa-stack/web dev`   | Serves the console with Vite's development server; what it asks under `/api` goes to the API of an instance on `127.0.0.1:8080`. |
| `oqas --ui`                              | Serves the built console and the API of a test repository on one address, in one process: see [the command](../cli/docs/oqas-command.md#the-console). |
| `pnpm --filter @open-qa-stack/web build` | Builds the console into `apps/web/dist/`.                                                                                        |
| `pnpm check`                             | Type-checks, builds every package, the console included, and runs the tests; it fails if the console does not build.             |

The console reaches its instance under `/api`, on its own origin, where the API serves its routes: the API serves the built console itself when it is given its folder, as `oqas --ui` has it do, or a reverse proxy sends that path to the API as it is, as Vite does while the console is developed.

## Layout

| Folder                        | What it holds                                                                                                                         |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `src/main.tsx`, `src/app.tsx` | The mount, and the application in a browser: it follows the address, names the page and moves the focus, beats a replay.              |
| `src/console.tsx`             | The console at a route: its screen in the shell.                                                                                      |
| `src/routing/`                | The route, read from the fragment of the address (`#/agent/sessions/<session>?show=talk`).                                            |
| `src/api/`                    | The client of the API, the one error every screen shows and its wordings, the poll of a call, the stream of a session, whether a session ended. |
| `src/i18n/`                   | The words of the console in each language the configuration names, read by i18next, and how it writes a duration and a date by `Intl`. |
| `src/shell/`                  | The frame of every screen: on a phone, a bar of the navigation alone, each entry an icon a finger presses; from 720 px, the mark before it; a sidebar from 1100 px wide that folds to its icons. |
| `src/ui/`                     | The components every screen shares, and their style sheet.                                                                            |
| `src/configuration/`          | The configuration: its form, the state of a draft and what keeps it in step with the instance, the words of the errors of its schema. |
| `src/agent/`                  | The sessions: the words of the console for the steps of a thread, which `@open-qa-stack/domain/sessions` reads from the events of a session for every presentation, how a session is followed or replayed, its thread, and the panel of a look. |

A screen is a function of what the API told and of its route: it holds no state and listens to no event. A filter or a selection is an address, so that every state of the console can be linked to, and tested by rendering it. The application alone holds state — what the API sent, and how each session is read — and hands it to the screen that shows it. No screen calls the network: `src/api/` does, with the types of `@open-qa-stack/domain/sessions`.

### How a screen gets its data

The state of the console is a reducer, `src/agent/console-state.ts`; `src/agent/console-sync.ts` keeps it in step with the instance, and is the only caller of `src/api/`:

- The project is read once, again only while the API fails to describe it.
- The sessions are listed again and again for the entry of the agent: a list is asked only once the one before was answered and two seconds passed, and none is asked while the tab is hidden. A list asked before a session was opened, which may lack it, is ignored.
- The session an address opens does not depend on that list: it is read by its identifier (`GET /sessions/:id`) on arrival, and again each time its stream says it changed state: when it started, and when it ended, to learn what it came to. “Session not found” is shown only when the API answers `unknown_session`.
- The events of that session come from its stream (`GET /sessions/:id/events`). The stream connects again by itself after any cut — a browser gives up for good on an answer that is not a success — each time after a longer wait, up to eight seconds, asking for the events `?after=` the last it received. It ends, and is not opened again, on the event that says the session no longer goes on; a session that waits its turn, `queued`, goes on: its stream stays open, and its thread simply goes on once its agents start.

Until a session ended, the person speaks to its agents from a composer under the thread, which stays at the bottom of the window: Enter or its button sends (`POST /sessions/:id/messages`), Shift+Enter starts a new line. Nothing is shown before the instance took the message: its bubble comes with the stream, “waiting for an agent” until the event that names the agent it reached, then “delivered to …” — in a replay too, where the delivery comes when it happened. Where the message is — sent, or refused and why — belongs to the session followed, in the state, and is forgotten with it; a refused message stays in the field. A message sent to a session that still waits its turn is delivered when its agents start. Once the session ended, the composer stays, and asks what the agents are to do next; its button reads “Go on with the session”: what the person sends resumes the session (`POST /sessions/:id/resumption`) for a new turn, which its stream tells under the verdict of the turn before, in the same thread.

While a session goes on — it runs, or waits its turn — its bar offers to stop it, and never stops it at one press: “Stop” is a link to the same screen with `?stop=ask`, an address like any other state of the console, which opens a confirmation under the bar. The confirmation says what stopping does, then offers the way out, “Cancel”, which takes the focus when it opens, and the button “Stop the session”, which alone asks the instance (`POST /sessions/:id/interruption`). While the request is on its way the button cannot be pressed again; a request the instance refused is told under it, in the wordings of the console, and the button asks again. Once the instance took the request, the confirmation closes and the bar says “stop asked…” where the link stood, which takes the focus: a session another process runs goes on until that process obeyed, and the console shows it “interrupted” only once its stream says so. Where the request is belongs to the session followed, in the state, and is forgotten with it. A session that ended offers nothing of it.

A session that did not change keeps the object the state already holds, so that what is computed from it is not computed again at every list.

Every failure of the API is an `ApiError` with the `code` of the problem the API answered, `error` when it gave none, or `unreachable` when no answer came. The console decides on that code alone: it words the codes it knows in its own words (`src/api/problem-text.ts`), shows the `detail` of the API otherwise, and says “Offline” only for `unreachable`. A value the console does not know — a state, a phase, an outcome, a type of event — reads as a neutral one, or is ignored: a later version of the API does not break an earlier console. One predicate, `hasEnded` of `@open-qa-stack/domain/sessions`, tells whether a session no longer goes on, for the console as for the conversation of the command line: it has not while it is `queued` or `running`, and has in any other state, one the console does not know included.

### The entry of the agent

`#/agent` asks what to test — its button waits for a word, and Ctrl+Enter in the field, or Cmd+Enter, presses it, Enter alone starting a new line — then what of the project to keep the session to, as chips under the request: the environment — chosen among those the configuration declares when it declares several — then the applications, the domains of the knowledge (`GET /knowledge/domains`, none before a cartography) and the levels, each every one until some are ticked. A chip opens on its list in the page, under the chips, and says what it takes: every one, the names ticked, or how many. The session is opened with them (`scope` of `POST /sessions`), and its facts say what it is kept to. Each session of the list then says what came of its tests as the executions do: the bar of their verdicts — passed, skipped, blocked, without a verdict, failed, not run left empty — the failures, the tests blocked and those without a verdict in words, and how many passed out of how many.

### The configuration

`#/configuration` holds the settings of Open QA Stack itself — the applications under test and the knowledge the agents read have [screens of their own](#the-applications) —: the configuration in force, kept by the instance as revisions, of which `oqas.json` is a copy written when the person asks, in a form the person changes, then saves:

- **What is changed**: the model — chosen in a list: the GitHub account of the machine, a provider by its name, or another server by its address; then tested, and picked among the models the connection offers, the effort, the wait and whether it reads images folded under « Advanced » —, the autonomy, the levels of the pyramid of tests a plan is asked for, the language of the console and of the agents and that of the tests, the layout of the test repository, and what the team asks of each agent — instructions added at the end of its prompt, or its whole prompt replaced from a copy of its own (`GET /configuration/agents`), with what it may break, the variables it leaves out and its own prompt beside it, folded, open when it changed since. A secret is never asked for: the configuration names the variable that holds it.
- **What is read only**: the JSON of the draft; the history of the revisions, the latest first, with where each comes from — the file, the console, or `oqas config export`.
- **The connection to the model** is tested by the instance (`POST /configuration/model-connection`) when the person asks: the card says in plain words what it found and what to do when it fails, and offers the models it found in a list. A test holds while the model is reached the same way.
- **Errors**: each draft is checked by the instance (`POST /configuration/validation`) as it changes, by the schema of `oqas.json` and its rules: the console validates nothing itself. Each error stands under its field, which it describes for a screen reader, worded by its rule (`src/configuration/configuration-words.ts`) — a field left empty is one to fill, whatever rule it breaks —, and all of them are counted at the head of the form, each with where it is in words, such as « Source pricing › Sert à 1 › Application » (`src/configuration/config-place.ts`). The errors of what the person changed show at once; the others, such as those of an item just added, once they asked to save. What an expert sets is folded under « Advanced », which opens by itself on an error of one of its fields: the identifier of an application, which follows its name while it is new; the variables that hold the credentials of an account and the connection string of a base, made of their names; the commands the agents may run in the code (`src/configuration/derived-names.ts`).
- **Saving** is explicit, by “Save” (`POST /configuration/revisions`), made from the revision the draft was read from: a change made from a revision another replaced since is refused, and “Discard the changes” takes the revision in force. A draft is kept while the instance tells a newer revision.
- **Short cards**: each setting shows what a person decides — the model, the level of autonomy, the levels of tests, the languages, the folder of the tests —, and folds under « Advanced » what an expert sets: the limits of the autonomy, the other folders of the repository. The history of the revisions, the file and the JSON are folded at the foot of the screen.
- **The file**: saving writes no file. Beside the history, a card says whether `oqas.json` holds the revision in force, differs from it, or is missing; “Write oqas.json” writes the revision in force to it (`PUT /configuration/file`), and “Take oqas.json” takes it as a new revision (`POST /configuration/synchronisation`).

**On an instance that has no configuration yet** — the file is missing and no revision was saved —, the screen is « Get started » (`src/configuration/first-use.tsx`): a welcome, which names the folder the project is written to and how to choose another — start the console again with `--repository` —, the applications, what the agents may read, the model, with the cards of the form, then a summary that says whether a git repository will be made, from `GET /repository`. « Create the project » saves the first revision (`POST /configuration/revisions` from `0`), then the values typed, then sets the test repository up (`POST /repository/preparation`), and the screen leads to `#/agent`.

**The values of the variables** — the key of the model, a connection string, an account of the tests — are typed beside the variable that names them (`SecretField` of `src/configuration/configuration-fields.tsx`), never in the draft: the screen keeps them apart, and « Save » sends them once the configuration that names them is saved, one `PUT /secrets/{name}` each, or alone when the configuration did not change; a value typed for a variable the environment of the instance sets is left out, since the environment wins. The screen reads where each value comes from with the configuration (`GET /secrets`): a value saved is offered to be replaced, never shown; a variable the environment of the instance sets is not asked for. The test of the connection to the model sends the key typed and not saved yet.

The state of the screen is a reducer of its own, `src/configuration/configuration-state.ts`, and `src/configuration/configuration-sync.ts` keeps it in step with the instance, reading the configuration and its revisions every two seconds. Its fields are named after the JSON Pointer of what they hold, which the reducer changes and the errors of the instance name; `src/configuration/use-configuration-editor.ts` holds that state in a browser, as `src/app.tsx` does for the sessions, for `src/configuration/configuration-page.tsx` and the screens of the knowledge; both are measured there.

### The discovery

`#/discovery` shows what the cartography found in the knowledge (`GET /knowledge/mapping`, `GET /knowledge/domains`), read again every few seconds: each source and where its cartography stands, when the knowledge was put together by domain, then the domains, each with what it covers, to pick. « Write the tests of these domains » opens a session kept to the domains picked (`POST /sessions` with `scope.domains`), whose request names them, and the console then shows it; a refusal of the instance stands under the domains. A domain is renamed in a panel, `?panel=rename:<id>`, excluded, or taken back (`PATCH /knowledge/domains/:id`): those excluded stand apart, and are not to pick. Before a cartography, the screen says no domain was found yet, and leads to the knowledge. `src/discovery/discovery-page.tsx` holds the screen in a browser, and is measured there.

### The applications

`#/applications` lists the applications of the configuration in force, each with its name, what it exposes and how many environments, APIs and test accounts it holds, leading to its page, `#/applications/<id>`: what it is, the sign-in of the users with the names of the variables that hold the credentials of the test accounts, and its environments — the address of the interface, the named APIs, what the exploration may do —, changed, saved alone as a revision of its own, and followed under the identifier it was saved with. “Add an application” (`?add=application`) adds an empty one to fill in and save, which then leads to its page; “Remove the application” (`?drop=application`) asks to be confirmed, saves a revision without it, and leads back to the list. A change not saved is dropped once the person goes to another page (`src/configuration/use-item-pages.ts`, which the knowledge shares). `src/applications/applications-page.tsx` holds the draft in a browser, and is measured there.

### The knowledge

`#/knowledge` shows the knowledge sources the configuration in force declares: those of the whole project first, then application after application — a source attached to several is listed under each — each with its kind, where it is read from, never a secret, the environment and the API it is narrowed to, and how many documents the instance keeps of it, with where its cartography stands (`GET /knowledge/mapping`): waiting, being mapped, mapped, or mapped in part. A line above says when the knowledge was put together by domain, or that nothing is mapped yet. “Add knowledge” (`?add=source`) offers each kind of source, then the source of the kind chosen, with the fields of the configuration: it is tested, then saved alone as a revision of its own, and the screen leads to it. Each source leads to its own screen, `#/knowledge/<id>`, where it is changed, tested and saved alone, then followed under the identifier it was saved with; “Remove the source” (`?drop=source`) asks to be confirmed, saves a revision without it, and leads back to the knowledge. A change not saved is dropped once the person goes to another screen of the knowledge. For a source declared `stored`, that screen lists its documents, by their names, each with its size and the date it was uploaded:

- **Reading**: the name of a document opens its text under the list, at `?document=<name>`, an address like any other state of the console.
- **Uploading**: a form takes one or more Markdown files. The console checks them first by the rules of an upload of `@open-qa-stack/domain/sessions` — their count, their names, their formats, their sizes — and sends nothing that breaks one; the instance then checks them again, their encoding with them (`POST /knowledge/:source/documents`). Each error stands under the field, which it describes for a screen reader, beside the file it is about; once the instance took them, the field is emptied and the screen says how many were uploaded.
- **Removing** is never one press: “Remove” is a link to `?remove=<name>`, which opens a confirmation that says it cannot be undone; its button alone asks the instance (`DELETE /knowledge/:source/documents/:name`), and the confirmation closes once it was taken.

The draft of a source is that of the configuration (`src/configuration/use-configuration-editor.ts`), of which the screen shows the source alone, so that nothing else of the configuration changes with it. The state of the screens is a reducer of its own, `src/knowledge/knowledge-state.ts`; `src/knowledge/knowledge-sync.ts` keeps it in step with the instance, reading the configuration in force and the documents of its stored sources every two seconds; `src/knowledge/knowledge-page.tsx` holds that state in a browser, and is measured there.

### The defects

`#/defects` lists the defects reported from tests that failed, kept by the instance (`GET /defects`), read again every few seconds, in three views, each with how many it holds: those to deal with, those fixed whose test is to run again, `?view=to_replay`, and those closed or whose test passed since they were fixed, `?view=closed`. Each line gives its reference, its title, its severity, where it stands, its test — a link to its card — and when it was reported, with what can be done of it: mark it fixed, close it, open it again (`PATCH /defects/<id>`); a move the instance refuses says why. A defect is reported from the card of a test whose last run failed: « Signaler l’anomalie » opens a panel, `?panel=report`, whose title and description the console writes from the failure — the step, the error, what was expected and received, the execution — for the person to change, with a severity from S1 to S4 (`POST /defects`); once kept, the console shows the defects. `src/defects/defects-page.tsx` holds the screen in a browser, and is measured there.

### The review

`#/review` lists the tests the agents wrote for a person to decide of (`GET /reviews`), read again every few seconds, in three views, each with how many tests it holds: the new tests to review, the updates of tests the agents propose — none yet —, and the tests set aside, `?view=updates` or `?view=set_aside`. The tests of a view are narrowed to a domain, `?domain=<id>`, kept from a view to the next. Each test of the list says its application and domain, its level, whether its last run passed and whether an agent reviewed it; the one shown, `?id=<id>`, is on its card (`GET /reviews/<id>`): its status, its level, whether it compares a screen, whether it was reviewed and ran; why it was written, by the agents, with the brief and the sources; what it verifies, step by step; what the agents that reviewed it said of its coherence and of its code; its code, folded, file by file; how many times it ran, and why it stands so. One set aside says why. J goes to the next test, K to the one before, but not while a field holds the focus. On a phone, the list gives way to the card alone, with where it stands in the list and links to the tests before and after it. « Valider », or V, validates the test shown (`PUT /reviews/<id>/decision`): it enters the working branch of the test repository, committed there, and the screen says where; « Écarter » opens a panel, `?panel=set-aside`, that asks why — already covered, with the test that covers it, out of scope, a wrong oracle, not at the right level — and a note. Once a decision is kept, the queue is read again and the next test shown; a decision the instance refuses says why, on the card. « Demander une correction » stays inactive, until the agents can take a correction. A view that lists nothing says all is reviewed, with a session to start, that no update came yet, or that nothing is set aside; one narrowed to a domain with no test says so, with the filters to clear. `src/review/review-page.tsx` holds the screen in a browser, and is measured there.

### The tests

`#/tests` lists the tests of the test repository, as their files are now (`GET /tests`), application by application — a test that crosses applications is under the first it names — each with its title, its path, its level, whether it compares a screen, its domain and functionality, and how many steps it has. The tests are narrowed to a level of the pyramid, `?level=<level>`, each with how many tests it holds, and to the words of a search in their titles, paths and tags, `?q=<words>`: the address keeps both, an address like any other state of the console.

The state of the screen is a reducer of its own, `src/tests/tests-state.ts`; `src/tests/tests-sync.ts` keeps it in step with the instance, listing the tests every five seconds and keeping those it listed last while the instance does not answer; `src/tests/tests-page.tsx` holds that state in a browser, and is measured there.

Each test leads to its card, `#/tests/view?path=<path>`: what the test is — its title, its path, what its tags say of it, and its steps as its file writes them, without what came of them — and what came of it lately (`GET /tests/executions`): its latest verdict and when, how many of its latest ten executions passed, with a dot for each, the oldest on the left, and the way to its latest result; its versions (`GET /tests/versions`), the latest first, each with when it was first run, how many executions ran it, and the commit it was first run committed at, or that it never was, as a version a design ran before committing it; then each of its executions, the latest first, with its verdict, its origin, the version of the test and the commit it ran at — said not committed when the test differed from it —, and its duration, leading to what came of the test there. A test whose last run failed says what to do: read its result first, then ask the agent, whose entry opens with the request written, `#/agent?request=<text>`, for the person to send. The tests of the repository show beside it by domain, every one or, `&tree=failing`, those whose last run failed (`GET /tests/verdicts`). A test no longer in the repository says so, and still lists its executions. Its action, « Relancer ce test », runs its file again as it is, with no agent (`POST /launches`), against the environment chosen when the configuration declares several; the card follows the launch, says when it ran, and reads its executions again once it ended. An execution launched so, or for a campaign, says it on its screen, which leads to the campaign; in the table of the executions, one launched for a campaign is named after it, and leads to it.

### The executions

`#/executions` shows the executions of the tests the instance keeps a page at a time (`GET /executions`), the latest first, as a table: when each ran, where it comes from — `design` for the tests a session ran —, the session that asked for it or how many tests it ran, and the environment they ran against when the instance kept it, how many of its tests failed, passed only on a retry, passed or were skipped, how long they took together, and the commit of the test repository. A line unfolds into its tests, the failures first, each with the step it failed at and what its assertion expected and received — or the first line of its error —, each leading to what came of it there, and leads to the execution. Lists narrow the executions: to those where a test failed or none did, `?outcome=failing|passing`, to those of an origin, `?origin=design|manual|campaign`, to those of a campaign, `?campaign=<id>`, and to those of the last day, seven days or thirty days, `?period=day|week|month`, counted back from each reading; choosing one opens the first page, and a last list chooses how many a page holds, `?size=25|50|100`. The launch that runs shows above them, on the first page, unless they are narrowed to what it is not or by what came of their tests: it leads to `#/executions/running`, which tells how far it went and each test it finished (`GET /launches`), then opens the execution it kept. The tests a session runs show once the session kept their execution. A page goes on after the last execution of the one before it, `?before=<id>`, and says which of them it shows, such as “1–25 of 132”: the address keeps the filter and the page. On a phone, a line keeps its date and its counts. A date is written to the minute, its month abbreviated, such as “19 Nov 2026, 02:16”, on every screen of the console.

`#/executions/view?id=<id>` is the screen of an execution (`GET /executions/<id>`): the figures of its tests — passed, failed, skipped, fixed, and how long they took —, the session that ran it and the version it ran at, then its tests as a table for each application, the failures first: the verdict, what changed since its last run — a new failure, one that failed already, a test fixed —, its title, its domain as the repository says it now (`GET /tests`), and its duration. A search narrows them, `&q=<words>`. It opens on those to look at, the failures and the tests fixed, or on every test when there is none; the others are a view away, `&view=all|new_failures|fixed|flaky`, each with its count. Its action, « Relancer les N échecs », runs the files of the tests that failed again (`POST /launches`), whole, and leads to the execution the launch kept; an execution launched for a campaign leaves it to the campaign.

`#/executions/result?id=<id>&path=<path>` is what came of a test in an execution, read in steps from the run of that execution (`GET /tests/reading?execution=<id>`), as a person checks it: how it ended, in one sentence — the step it failed at and out of how many —; what its failed assertion expected and received when its message says both; its steps, compact, each with its number, its state and its duration; and the page at one of them, whole width (`GET /tests/capture`): the step the address names, `&step=<number>`, or else the one that failed, which shows the page the runner captured at the failure when the test attached none of its own, or else the last one captured. The technical details are folded. Its crumbs lead back to the execution, and a link to the card of the test. An execution whose report is gone says so.

`#/executions/trace?id=<id>&path=<path>` is the trace the run of that execution kept of the test, which the screen of the result leads to when it kept one (`GET /tests/reading` says so with `traced`): the trace viewer of Playwright the instance serves beside the console, `/trace-viewer/`, opened on `GET /tests/trace` over the width and the height of the window, with a link that opens it in a tab of its own and one back to the result. A run that kept no trace says so.

`#/campaigns` lists the campaigns, the latest planned first, each with the bar of the verdicts of its tests and how many ran, beside the form that plans one: a name and an environment the configuration declares, and, folded, what may be said of it: its objective, the version it tests, its first and last days, and who is in charge. The version shows beside the environment of the campaign and of its executions. A campaign planned opens on the choice of its tests (`PUT /campaigns/:id/tests`): the tests of the repository, narrowed by words of their title or path, level, domain, application and tag, or to those chosen; each ticked one by one, or those shown at once; the choice kept when the person is done, and the campaign fixed only once its choice is kept. `#/campaigns/view?id=<id>` is one campaign: its life as steps, whether it passes once it is no longer planned — every test passed, at once or on a retry — which the list says too, its environment, how far it went — how many of its tests ran, the bar of their verdicts and a badge each — then its tests, the failures first, each with its verdict in the latest execution of the campaign that ran it, which leads to its result, or « non joué ». While its tests run, it follows the launch every second and a half: how many tests the runner finished out of how many, and the verdict of each test as soon as it finished. Its state allows its gestures: fix its tests while it is planned, launch them once it is ready, then launch again its failures, the tests not run, or all of them, and close it, which asks to be confirmed; the screen says why the instance refused a gesture.

Each of these screens asks the instance again every five seconds while it shows, by `usePolled` of `src/api/use-polled.ts`, and keeps the answer it had while the instance does not answer; the pages that hold that state in a browser, `src/tests/test-page.tsx`, `src/tests/use-relaunch.ts` and the `*-page.tsx` of `src/executions/`, are measured there.

### Languages

The console speaks the language the configuration in force names, `language` of `oqas.json`, English by default: it reads it from the instance (`GET /configuration`) when it opens, and again once a change of the configuration was saved, then switches every screen at once. Until it read it, and while the instance has no configuration yet, it speaks the language of the browser when it has its words, English otherwise: « Get started » saves that language in the first configuration. There is no other setting: one place decides, for the console, the conversation of the command line and the agents alike.

Its words are those of [i18next](https://www.i18next.com), with [react-i18next](https://react.i18next.com), in one JSON file per language under `src/i18n/`, with the same keys in each, which a test checks; the keys of `en.json` type every call. A count is written in the singular or the plural by the rules of its language, a duration and a date by `Intl`. What the agents and the harness wrote is shown as they wrote it: the console translates none of it. The tests of the console read it in French, which `test/in-french.ts` sets before each file; `test/i18n/` reads it in English too, and so does a test of the layout in a browser.

## Styles and design tokens

The style sheets are written for a phone first. The rules of a sheet lay out a narrow screen; a wider one only adds to them, in `@media (min-width: …)` blocks — no sheet holds a `max-width` query — at two widths:

| From    | What it adds                                                                                                                                                                               |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 720 px  | A line holds more: wider gutters, the role of an agent beside its name, the state of a session beside its facts. |
| 1100 px | A desktop: the navigation as a sidebar, with the project and what is coming, which a button of the top bar folds to its icons and unfolds — the browser keeps it for the next visit, and the screen of a trace opens with it folded, whatever is kept; what an agent had before its eyes as a drawer at the right; lower controls, pointed at rather than pressed. |

A session is its thread alone, in one column that starts where the title of the page does. What an agent had before its eyes when it acted opens on demand, from the eye of that action, which names it in the address (`?look=6`): a panel that covers the screen below 1100 px, a drawer at the right from there, which the thread makes room for. The panel is titled by what it shows: “Page looked at”, under the application and the address of the page, or “Test file”, under its path — the file of a test can be opened as soon as the agent hands it to a tool, while the test runs. The line of a run names the test, says how it ended and where the file is, and unfolds in place on the verdict of each test the run ran, what the tool answered when the run did not pass, and the code. The code of a test, in the panel as in the line of a run, is coloured by [Shiki](https://shiki.style) with the grammar of TypeScript and its engine of regular expressions in JavaScript, in a theme whose colours are variables of the sheet (`.code` in `src/ui/ui.css`), so that it takes the colours of the console: Shiki and the grammar are loaded apart, the first time code is drawn, and until then, or if they cannot be loaded, the code is drawn plain. A count is written in the singular or the plural as the language of the console has it, by i18next. Its link “Close”, the Escape key and the way back of the browser close it; the focus goes to its title when it opens, and back to the eye when it closes. An address whose `look` names no action that looked at something opens nothing. The name of an agent, in the thread, follows that agent (`?agent=planner`): the thread then shows it alone. The filters of the thread keep what is said (`?show=talk`), the notes of the harness included; what is done (`?show=actions`); or the verdicts (`?show=verdicts`), of the harness and of the reviewers alike, with the plans it accepted and the verdicts of the tests. Below 1100 px all that is pressed is 44 px high and wide at least, and a field is written at 16 px, so that a phone does not zoom on it. What moves does so only under `prefers-reduced-motion: no-preference`.

Every text a thread holds is shown whole: what an agent and the harness say, a verdict, a note, the answer of a tool, what an agent looked at. A verdict, of the harness or of a reviewer, is one form of card: its author first — “Harness”, marked “automatic check”, or the agent that reviewed, marked “reviewing agent” — then what it came to, the code of the gate that refused, what it is about (the phase, the scenario, the tool, or what the reviewer reviewed), what it says, and what it was told with under “Details”: the text of the harness as it wrote it, or the call of the reviewer. A refusal of the harness is read by its form: what was refused, then why and what to do, the page it quotes folded under its address. A reason too long for a few lines shows its first six lines over a button “Read more”, which unfolds it in place and says so to assistive technology (`aria-expanded`), then “Fold”; which texts are unfolded belongs to the session followed, in the state. A one-line ellipsis is left only where the whole text is one press away or already on the screen: the first line of a reasoning, of a row of notes and of an action, in the line that unfolds it; the title of the session in the breadcrumb, under which the page is titled with it; the name of the project in the sidebar, which the top bar shows whole beside it. What the session works on opens its thread, as soon as its configuration is resolved, in a card every filter keeps: the levels of the pyramid of tests asked, which alone are designed, the applications and the environment, with the key of the configuration that sets the levels. A plan the harness accepted is a card with a cell for each scenario, folded to its level, its title, its case and its application: a cell unfolds on all the plan says of it — what it verifies, its facts, its sources, its data, each step with the texts it expects the screen to show or no longer show — then on the scenario as the event told it, folded under “Details”. The refusals of the harness about a scenario before its plan was accepted are counted on its line and told under its steps. The notes of the harness that say the same of several sources in a row, such as the cards it kept because they were up to date, are one line, what they say around the name of a source and how many sources, which unfolds on each note: the fold of the thread groups them, for the terminal too.

Each selector is styled in one sheet, the one of its component, and `src/main.tsx` imports them in this order: `src/tokens.css`, `src/base.css` (the page, links, the focus ring, the utility classes), `src/ui/ui.css` (the shared components), `src/shell/shell.css`, `src/agent/session.css`, `src/agent/agent-home.css`.

Colours and geometry are CSS custom properties, declared on `:root` in `src/tokens.css` as a phone needs them; the same file changes, for the wider screens, the few that change. That file is the only place a colour is written: every other style sheet, component and page refers to a token with `var(--name)`, and a test fails on any colour literal (`#fff`, `rgb(…)`, `hsl(…)`…) or named colour (`white`) written elsewhere. It reads every page, style sheet, drawing and script of the package, outside `node_modules/`, `dist/` and `test/`: colour literals anywhere in them, named colours in CSS declarations, in the attributes and style elements of `.html` and `.svg` files, and in the string literals of scripts and components. The name of a token is read as a word too: one that is the name of a colour, such as `--canvas`, fails.

To add a token:

1. Declare it in `src/tokens.css`, next to the tokens of the same family (`--primary-soft` beside `--primary`).
2. Use it with `var(--name)` where it applies.
3. Add its name and value to `REFERENCE_TOKENS` in `test/tokens.test.ts` if it is a reference token of the design — every token of the geometry is one; a secondary colour goes to `SECONDARY_COLOURS`.

### Geometry

No sheet writes a length of its own. Every margin, padding, gap and offset, every radius, every size, line height and weight of the text, every border and shadow is a token, or `calc()`, `min()`, `max()` of tokens; `0`, `auto` and percentages are the only literals. `test/geometry.test.ts` fails on anything else, on a custom property declared outside the tokens file, and on a scale that breaks one of the rules below.

**Spacing.** One scale, on a grid of 4 px: `--space-1` `-2` `-3` `-4` `-6` `-8` `-12`, each named after its count of 4 px (4, 8, 12, 16, 24, 32, 48 px). Sizes are on the same grid: a control (`--control`, 44 px, 32 px on a desktop), a row (`--row`, 48 px, 32 px on a desktop, so that the line inside its hairlines stays a finger high on a phone), what a finger presses (`--tap`, 44 px, 24 px on a desktop), the top bar (`--bar`), the pictures of who speaks (`--picture` 32 px, `--picture-sm` 20 px), the columns. An icon is drawn at 12, 16, 20 or 24 px, its line 1.5 px thick at every size.

**Proximity.** What belongs together stands closer than what does not, by a factor of two at each level:

| Token        | Step  | Between                                                                                                    |
| ------------ | ----- | ---------------------------------------------------------------------------------------------------------- |
| `--gap-line` | 4 px  | a line and what hangs under it: the answer of a tool, the status of a message, the source of a scenario    |
| `--gap-row`  | 8 px  | the rows of one turn; the harness that hands the work over and the turn it opens; the head and text of a card |
| `--gap-turn` | 16 px | two turns of the thread; the bar, the passes, the filters and the thread of a session                      |
| `--gap-pass` | 32 px | a pass and what came before it                                                                             |

On a line, the parts of a row are 8 px apart, a dot and its word in a pill 4 px; a surface is padded at least as much as what it holds is spaced.

**Radii.** A surface set in another takes the radius of the outer one less the padding between them, rounded down to a step, and the least step when nothing is left; it never takes more than what holds it.

| Token              | Radius | Taken by                                                                                                        |
| ------------------ | ------ | --------------------------------------------------------------------------------------------------------------- |
| `--radius-panel`   | 16 px  | what frames controls 8 px from its edge: the bar of a session, the field of the composer and of the entry; a bubble |
| `--radius-card`    | 12 px  | a card: the list of the sessions, a verdict, a plan, a result                                                    |
| `--radius-control` | 8 px   | a control (16 − 8), the row of an action, a frame, the picture of an agent (a quarter of its side)               |
| `--radius-inner`   | 4 px   | what a row or a card holds: the eye of an action (8 − 4), a code, the answer of a tool, a small picture           |
| `--radius-pill`    | —      | chips, badges, dots                                                                                              |

**Type.** One modular scale, 14 px times a power of 1.125 (a major second, the gentlest ratio that still tells two neighbouring roles apart in a dense console), rounded to the pixel; a line height on the grid for each role; three weights (400, 500, 600). The scale is the same at every width: the field a person types in is 16 px on a phone because the reading role is, and a desktop gets its density from lower controls, not from smaller text.

| Role      | Token            | Size / line | For                                                              |
| --------- | ---------------- | ----------- | ---------------------------------------------------------------- |
| caption   | `--type-caption` | 11 / 16 px  | times, badges, labels in capitals, code                          |
| small     | `--type-small`   | 12 / 16 px  | what is said beside: roles, facts, notes of the harness, chips   |
| body      | `--type-body`    | 14 / 20 px  | the console: actions, buttons, the navigation, rows              |
| reading   | `--type-reading` | 16 / 24 px  | what is read or typed: what an agent says, a verdict, a request  |
| heading   | `--type-heading` | 18 / 24 px  | the title of a panel                                             |
| title     | `--type-title`   | 22 / 28 px  | the title of a page                                              |
| display   | `--type-display` | 28 / 36 px  | the question of the entry                                        |

What is read at length — what an agent says, a verdict, a note — keeps to `--measure`, 64 `ch`, about 70 characters a line.

A note of the harness, small text in a line or two, takes the wider `--measure-wide` (96ch).

**Keylines.** A page has one left edge, its gutter: the breadcrumb, the title, the bar, the passes, the filters, the thread and the composer start on it. The thread has a second one at every width, `--keyline`, the picture of an agent plus the gap beside it: what an agent said and did, the lines and the notes of the harness, the verdicts and the cards start there. What a surface holds is set in by `--pad`, a row and a card alike; the text of a line of the harness starts after the room of its mark. At the right, every time ends `--pad` from the edge of the column: the time of a turn, of a card, and of an action, whose eye stands in a column before it.

**Lines and elevation.** A border is `--hairline` wide; a focus ring and an accent are `--stroke`. A surface stands at one of two heights: resting on the page (`--elevation-rest`), or raised over what scrolls under it (`--elevation-raised`: a bar that follows the page, the composer, the drawer).

## Tests

The tests run with Vitest. Components and screens are rendered in Node with `react-dom/server` and read as a person reads them: their text, and where their links lead. The layout tests build the console with Vite and use it in Chromium, at the widths of a phone and of a desktop, where they check what overflows, what a finger can press, and how the look of an action opens, closes and moves the focus: its files are answered from the build, and what it asks the API is answered by the test, which plays an instance (`test/played-instance.ts`) whose session goes on, completes or is interrupted once it was asked to stop, which opens a session that waits in the queue until it starts, whose stream is refused then opens again, which takes a message and delivers it or refuses it, which answers a problem, or which cannot be reached.

The coverage of Node counts only the modules a test loads there, and two modules only run in a browser: `src/main.tsx`, which mounts the console, and `src/app.tsx`, which follows the address, names the page, moves the focus, closes a look on Escape, asks for the stop a person confirmed and beats the clock of a replay. A layout test measures them in Chromium instead, maps the coverage of the build back to their lines through its source map, and fails on any line that did not run. The manifest lists them under `coverage.measuredInBrowser`, so that `pnpm check` leaves their coverage to that test. Keep them small: what can be a function of its arguments belongs in a module Node tests.

`tsconfig.json` type-checks the console against the browser's types only, so code that needs Node does not compile; `test/tsconfig.json` adds Node's types for the tests.
